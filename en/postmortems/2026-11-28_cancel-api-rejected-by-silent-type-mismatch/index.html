An Order-Cancel API Rejected Our First Real Call - A Silent Type Mismatch and a Swallowed Error

2026-11-28

We sent an order number as a string where the external API wanted an integer, the cancel was rejected, and the error path threw away the real reason and logged only "no response" - so the cause was hidden twice

This is the English version of a post originally written in Korean for my algorithmic trading system devlog(new tab).

My automated trading system has a path that cancels an order and re-plans it when the order doesn't fill within a certain time.

This isn't part of the stock-picking logic — it belongs to the order execution/safety layer, whose full design I've written up separately in the live-account post(new tab).

The day this "auto-cancel an unfilled order" path fired for real on the live account for the very first time, that cancel was rejected.

What happened

One day an order went unfilled past its time limit. By design, the system was supposed to cancel it and hand it off to re-planning.

But the cancel didn't take. The unfilled order just stayed in the account.

The log, for the cancel attempt, said only "no response." As if the broker side had given no answer at all.

In effect, the one safety path I turned to only when I actually needed it had failed silently.

What I thought at first

At first I assumed it was a transient network or broker-side issue. I took the "no response" log at face value.

Maybe a timeout, or the broker API being briefly flaky at that moment. If that were it, a retry would fix it.

But resubmitting the same cancel gave the exact same "no response." A transient fault wouldn't reproduce 100% of the time.

That's when I started to doubt the log message itself. Did "no response" really mean no response came back, or did a response come back and just get reported that way?

The real cause — two layers

The cause split into two layers.

Layer one: we sent the order number as the wrong type.

A cancel request has to carry the original order's number. And the broker API expected that order-number field to be an integer.

My code was converting that value to a string before sending it. It's a number-looking string, so it looks identical to a human eye — but to the API it was a type-wrong request.

So the broker rejected the request outright with an HTTP 400 and a vendor-specific error code. The cancel was never even attempted.

Layer two — and this is the real lesson: the error path threw the real reason away.

The broker clearly put the rejection reason in the 400 response body. In other words, the "why it was rejected" was already in my hands.

But the error-handling code wrapping the cancel simply discarded that 4xx reason and left only a generic "no response" message. It swallowed the error body whole without reading it.

So a precise diagnosis — "rejected with a 400 because the type was wrong" — had been turned into the vague sentence "no response." The cause was hidden twice: once by the type bug, once by the log that ate the error.

Why it had never surfaced: this path ran on the live account for the first time.

The auto-cancel path had existed in code for a long time, but it had never actually fired on the live account. The situation where an unfilled order reached that condition was itself rare.

The unit tests ran against a mocked broker. The fake broker happily accepted either a string or an integer.

So the real API's contract — "the order number must be an integer" — had never once been verified by a test. Right up to the moment it met the real broker for the first time, the bug sat there quietly alive.

How I fixed it

The fix addressed each of the two layers.

First, I normalized the order number to an integer right at the boundary, just before sending it to the broker. However the value is carried around internally, the point that touches the API now always sends it in the expected type.

Second, I changed the error path to surface the 4xx reason it received instead of discarding it, writing it to the log and the alert. Now if the same kind of rejection happens again, it prints the actual reason the broker returned — not "no response."

Finally, I added a regression test that pins the order-number field to go out as an integer. The contract that a lenient fake broker let slip is now something a test holds onto explicitly.

Only after watching a full cancel succeed on the live account did I trust this path.

Generalizing

An external API's type contract isn't enforced by your type checker. A number-looking string flows through your own code without a hitch. Then the moment it crosses the external boundary, the other API rejects it, saying "I wanted an integer."

This is worth normalizing explicitly at the boundary. "What type did I carry it as internally" and "what type must it be when it goes out to the API" are different questions.

Check that your error-handling code doesn't swallow the one thing you need. The worst log isn't a wrong log — it's one that's technically correct but useless. "No response" wasn't a lie, but by hiding the 400 reason I already held, it sent me the wrong way (suspecting the network).

When you wrap an external call, don't flatten the failure into a generic phrase — keep the status code and response body as they came. Debugging turns on that one line.

For a path that almost never runs, "first real use" is the first test. Recovery, cancel, and fallback paths sit idle most of the time and then run for the first time exactly when things are urgent. And that's when they first actually collide with the external contract.

Mocks are convenient, but they don't imitate the other side's strictness. The more lenient your fake dependency, the more the real contract gets verified for the first time in production.

So now I ask "has this path ever actually run against the real environment" as a question separate from whether the tests pass. Even with a green test suite, the first time code crosses an external boundary is, in itself, still an unverified event.
