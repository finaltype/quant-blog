Execution-layer defects found by code review - false alarms and order-cancel ordering

2026-11-26

Two weeks after going live, I handed the whole batch of recent changes to an external code review, got 8 important defects and 26 improvement suggestions, and folded them all in within a day. I fixed a bug where failed orders were summed into a reconciliation alarm, and a race between canceling unfilled orders and claiming buy slots.

This is the English version of a post originally written in Korean for my algorithmic trading system devlog(new tab).

Handing two weeks of changes to a code review at once

Since going live, quite a lot of hastily patched code had piled up over two-plus weeks.

Patching each situation as it first surfaced in real trading, I'd made fixes that were each correct on their own — but I'd never gone back and re-read the whole thing.

So I handed everything that had changed in the last two weeks to an external code review (a different AI tool) in one pass. The result: 0 critical defects, 8 important ones, and 26 improvement suggestions.

No critical defects was a relief. But the 8 important ones were almost all clustered in the order execution and safety layer(new tab).

That's the layer closest to real trading, where I'd rushed the most fixes — so in hindsight the distribution made sense.

A reconciliation guard that cried wolf

The first thing I fixed was the reconciliation guard in the daily execution summary.

This guard sums up the order amounts that went out that day and checks them against the account ledger. If the numbers don't line up, it raises an alarm that "something leaked."

The problem was that it was also counting orders that had failed to be accepted, or were never submitted at all. It was counting money that never actually went out as if it had — so of course the sum didn't match, and the guard fired a false alarm.

I fixed it to exclude failed and un-submitted orders from the total.

When a safety device keeps crying wolf, you eventually start ignoring the real alarms too. That's more dangerous than missing the leaked money.

Ordering of cancellation and buy-slot claiming

The auto-cancellation of unfilled orders I added yesterday drew one note too.

In the morning, the step that cancels the previous day's unfilled orders could run before the step that claims that day's buy slots.

If the two overlap on the same resource, cancellation and fresh allocation can get tangled. So I moved the cancellation to run after the slot claim succeeds.

I also set the minimum wait before re-submitting an unfilled order a bit longer. Re-ordering too soon risks doing so while the original order is still filling.

Early market close on exam day - manual procedure over modeling

Separately from execution, I made one operational call on the calendar side.

The Korean stock market shifts its open and close times on exactly one day a year: the national college entrance exam day. I debated whether to bake this exception into the calendar logic as a "model" and handle it automatically.

I decided against it. Generalizing a once-a-year exception into code just means that code sits dormant most of the time and risks going off at the wrong moment.

So I documented it as a manual procedure used only on that day, with an alert that fires as the date approaches. There was a past incident where someone forgot to register the special opening-time table and a timer fired at the wrong hour — so I also made that very omission raise an advance warning.

Melting every exception into code isn't always the right answer. Sometimes "a human touches it once that day" is safer.

Owner-pinned buying - a separate lane apart from the bot's judgment

Finally, I handled a directive from the owner to accumulate one specific stock in small daily amounts.

This has nothing to do with the bot's automated stock selection — it's purely the owner's personal decision. Wedging it into the selection logic would contaminate the bot's judgment.

So I built a separate "pinned buy" lane, apart from the bot's automated buying. I also registered this one case as an explicit exception, with an approval record, to the config-change freeze I'd put in place earlier.

One more thing I made sure of was performance measurement(new tab).

A holding the owner pinned like this isn't something the bot picked. So I made it get excluded entirely from the sample used to tally strategy performance.

If the price moves of a stock the bot didn't choose get mixed into the bot's performance, you'll later misread "how much does this system actually earn." Drawing a clear boundary around measurement is the point.
